How much real-world Rust can h5i-app verify?

Security logic from six open-source Rust servers, ported to h5i-app and stated as 103 Lean 4 theorems. We measure how many are proved, how much upstream code they cover, and how fast the port runs.

verified

Proved specs, the upstream code they cover, and project checks. A theorem proves one property of a function, not all of its behavior.

Specs accepted

Upstream lines reached
Lines of the upstream functions accepted theorems are about, over those all selected theorems are about. No blanks or comments.
Of kernel ceiling
Reached lines over the module's kernel ceiling: the lines that could be a kernel at all (pure, synchronous, no I/O, clock, randomness or locks, transitively). A static estimate; see harness/kernel_ceiling.py.
Gate
h5i app check. Passes once every spec is proved.

performance

Kernel time ÷ upstream time on the same inputs, release builds on one host. Below 1× the port is faster. Hollow marks: one side does extra work, such as database calls.

method

How specs are built and checked.

  1. Rust

    Upstream code

    Security code of an open-source server, at a pinned commit.

  2. Rust

    h5i-app port

    Ported function by function. Each change is listed in DEVIATIONS.md.

  3. Lean 4

    Extracted model

    Aeneas turns the port into Lean. A spec states each property.

  4. Prover

    Proof

    Agents in an offline sandbox, 30 minutes per try, or by hand.

  5. Checker

    Accepted?

    Re-checked in isolation, then gated by h5i app check.

Differential tests. Upstream and port must agree on random inputs. Testing, not proof.

Corrections. A false spec gets a recorded precondition, never a silent change.

  • Proofs cover the kernel. Parsing, database and I/O around it are trusted.
  • Coverage counts code a theorem is about, not code whose every behavior is proved.
  • Timings are pilots on one host.
