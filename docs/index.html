How much real-world Rust can h5i-app verify, and what does it cost at runtime?

Six open-source Rust servers had their security-relevant logic (access control, input validation, parsing) ported to h5i-app, extracted to Lean 4 with Aeneas, and specified as 103 theorems. We track how many of those theorems are proved and independently re-checked, how much upstream code they reach, how much Lean it takes, and how fast the verifiable port runs next to the original.

verified

Per application: selected specs whose proof passed an independent re-check, the upstream code those theorems are about, and the project-level checks. A theorem about a function proves one property of it, not its whole behavior, so reached is not fully verified.

Specs accepted
Theorems whose proof built against the pinned statement, generated Lean, spec and library, with only propext, Classical.choice and Quot.sound. Certificates are re-checked in an isolated workspace, not taken from an agent's report.
Upstream lines reached
Lines of the pinned upstream functions that accepted theorems are about (statement targets and their callees, deduplicated), out of those that all selected theorems are about. Blank lines, comments and attributes are not counted.
Ported / module
Upstream lines with a ported counterpart, out of the selected upstream module scope; both count nonblank physical lines. It shows how small the verified core is compared with the surrounding application.
Gate
h5i app check on the canonical project: it passes only once every selected theorem is proved and integrated. Until then it fails on the remaining sorrys.

performance

Kernel time divided by upstream time for the same inputs, compiled Rust against compiled Rust (release build, same compiler and host). Below 1× the verifiable port is faster. Filled marks compare matched boundaries; hollow marks include unequal work on one side (database round trips, request construction) and do not measure the kernel alone.

method

How a spec is made, what counts as verified, and where trust ends.

  1. Rust

    Upstream code

    Access control, validation and parsing code of an open-source server, at a pinned commit.

  2. Rust

    h5i-app port

    Ported function by function. Strings become byte slices, iterators become loops; every change is listed in the port's deviations file.

  3. Lean 4

    Extracted model

    Aeneas extracts the port, so the Lean is the code that runs. A hand-written spec states each property as a theorem.

  4. Prover

    Proof

    Any proof source: coding agents in a network-less sandbox (30 minutes per attempt) or interactive sessions.

  5. Checker

    Accepted?

    Re-checked in isolation: builds, statement unchanged, standard axioms only. Then integrated and gated by h5i app check.

Differential tests. Upstream and port run on the same random inputs and must agree; a mutated port must fail. Evidence, not an equivalence proof.

Statement corrections. A spec proved false is never silently weakened: each added precondition is recorded with its counterexample.

  • A theorem certifies the extracted kernel under its stated preconditions. The shell around it (request parsing, database access, I/O) is the trusted boundary.
  • Coverage counts upstream code that accepted theorems are about. It does not claim that code's full behavior is proved.
  • Timings are pilot measurements on one host. Ratios from unequal boundaries are shown but are not kernel speedups.
