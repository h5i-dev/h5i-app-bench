GPU cart pricing

django-cart 3.1.1 · 2026-10-19. Recalculate already-loaded cart snapshots.

Compare Rust, Go, Node.js and CUDA using identical cart snapshots. Select lines per cart to see how batch size changes the result. Milliseconds per complete batch, lower is faster; median of three repetition means. Hover over a timing for its measured range.

GPU resident reuses unchanged input; upload each transfers all snapshots every call. Both download all totals. A CPU could cache unchanged totals too; useful residency needs changing prices or discount scenarios, including synchronization costs. See candidate workloads and evaluation requirements. This is an offline calculation microbenchmark. For HTTP request coalescing and SQL query batching, see django-cart totals and the 32–2,048 lines/cart comparison above. Session handling, database aggregation and checkout transactions are excluded. This does not establish a speedup over a Django deployment.

Run conditions and correctness
  • EPYC 7502, CPUs 64–79, RTX 3090 device 0, CUDA 12.6. Eight warmup passes; three repetitions, each averaging 100 iterations below 4,096 carts and 10 otherwise; shared host and uncontrolled clocks/NUMA placement.
  • GPU snapshots are transposed on upload for contiguous reads; upload-each timing includes that conversion. The same integer pricing source runs on CPU and CUDA using h5i's NVVM launch shell. CPU 16 uses persistent Rayon workers. GPU resident timing includes launch, synchronization, result allocation, download and error validation.
  • 4,146 cases agree with the pinned upstream's Decimal methods; 49 exercise its ORM aggregate. Rust, Go, Node.js and CUDA agree with this corpus. CPU/GPU checks also cover malformed snapshots and batch boundaries. This pricing kernel has no Lean proof.
  • None, percentage and fixed discounts, final half-up rounding, default zero tax/shipping. Fixed-width snapshots reserve 32 lines; no mutations or live cache invalidation are measured.

Compact cart updates and pinned buffers

32-byte versus 8-byte replacements, with pageable or reusable page-locked host staging.

All paths consume the same canonical commands and return a fresh owned vector of every queried total. Encoding and staging copies are timed. A compact replacement packs slot (11 bits), price (27) and quantity (10); cart ID comes from the validated round-robin query order. Query IDs remain explicit. This format requires that routing contract. Compact encoders run on one or four workers; encode4 uses the same persistent Rayon pool and four-core budget as CPU4. Pinned paths copy/encode into reusable locked input, queue upload/kernels/full download in one stream, wait, then copy locked output into an owned vector. There is no overlap across batches. Initialization is separate.

Plain runs drive comparisons. Event runs are separate diagnostics: upload, kernels and download use the same stream. Pageable upload intervals include possible host submission gaps; they do not isolate DMA. Event readout is included in the diagnostic total. Resident cart updates across languages

Go, JavaScript, Python, NumPy, Rust and GPU: the same changing input and every total returned.

Every path retains rows, subtotals and totals between batches. Canonical commands contain explicit u64 query IDs and four u64 fields per replacement. Timings include applying updates, pricing, worker dispatch/join and a complete freshly owned output. GPU paths also include encoding where applicable, upload, synchronization and full download. All returned values are checked exactly outside timing. No SQL/HTTP is included.

One or four persistent computation workers; Python 4 uses fork processes, JavaScript 4 uses worker threads, Go 4 uses goroutines, Rust 4 uses Rayon. NumPy is a separate native vectorized implementation with native thread counts fixed to one. All modes share the same four-core allocation (CPUs 64–67), with GC enabled. CPU timings are collected without concurrent benchmark processes. If GPU references from the prior run are shown, their status is explicit above and their ratios are not contemporary speedups. JavaScript uses exact Float64 integer subtotals and quotient/remainder discount rounding. CPython loops use Python integers with u64 retained storage; NumPy is used for untimed input validation in every Python mode.

Initial placement, loading, worker creation and validation are excluded. Python imports initial subtotal caches from fixtures, computes initial totals itself, and independently rescans subtotals for every upstream gate; other languages construct their initial caches. Initialization timings are not comparable cache-construction costs. Three repetitions, eight changing warmups and 50 changing timed rounds; RTX 3090 device 0. Shared host; clocks, NUMA and cache placement are uncontrolled. This is a resident calculation/update benchmark, not a Django deployment speedup.

Method

Overview runs: fresh seed, 10 s warmup, 30 s measurement, mean of three repetitions. Targeted experiments list their own conditions.

  • Servers, PostgreSQL and k6 use separate CPUs. Serial runs give each server 4 cores: 4 workers for Python, Node and Go; 4 Tokio threads for Rust.
  • Requests/s includes k6's graceful stop. Latencies are per-run percentiles; RSS is peak memory across the server process tree.
  • Login uses bcrypt cost 12, which dominates that scenario.
  • Single-host measurements. Scripts and CSV results: performance/.
