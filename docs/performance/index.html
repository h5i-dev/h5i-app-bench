GPU search

Linkding · 2026-10-17. The same server with CPU or GPU search over a resident index.

Full HTTP requests, including authentication, SQL, pagination and JSON. At 16 clients, GPU search is 6.94× faster for simple search and 12.51× for complex search than the resident CPU version.

Run conditions
  • 100,000 bookmarks, 2,000 tags, 50 users. Simple and synthetic eight-term searches each match 1,000 active bookmarks; the first page returns 20.
  • Dual EPYC 7502, RTX 3090. Four concurrent variants, each with 4 server, 4 PostgreSQL and 4 client CPUs. Shared host; clocks and NUMA placement vary.
  • Three repetitions, fresh database/server, 10 s warmup, 30 s measurement. Index initialization is in warmup; mixed traffic includes rebuilding after writes. 128,022 measured requests; zero failures. Cost, power and cold start were not measured.

GPU policies

Conduit · 2026-10-18. The same server with CPU or GPU policy decisions.

CUDA handles eight authorization and state decisions. HTTP, SQL and serialization use the same code. The CPU kernel has Lean proofs; GPU behavior is tested against CPU results. List, slug and login are controls that do not use GPU decisions.

Run conditions

Method

Overview runs: fresh seed, 10 s warmup, 30 s measurement, mean of three repetitions. Targeted experiments list their own conditions.

  • Servers, PostgreSQL and k6 use separate CPUs. Serial runs give each server 4 cores: 4 workers for Python, Node and Go; 4 Tokio threads for Rust.
  • Requests/s includes k6's graceful stop. Latencies are per-run percentiles; RSS is peak memory across the server process tree.
  • Login uses bcrypt cost 12, which dominates that scenario.
  • Single-host measurements. Scripts and CSV results: performance/.
