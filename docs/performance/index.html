How fast is a verified web server?

The same REST APIs on the same PostgreSQL data, written in Rust on h5i-app (whose decisions are proved in Lean 4) and in Go, TypeScript and Python. Every implementation passes the same conformance suite, then runs under k6 at 1 to 256 concurrent clients.

Optional GPU search

Linkding HTTP API remeasurement · 2026-10-17. GPU acceleration is optional and especially useful for repeated, parallel text searches over a resident index.

These requests include authentication, database operations, search, pagination, tag fetching and JSON responses. At 16 clients, GPU throughput is 6.94× the resident CPU scan for simple search and 12.51× for complex search. CPU and GPU use the same application source and result path.

At 16 clients, p99 search latency falls from 201 to 46 ms; complex search falls from 1,131 to 90 ms. The existing read/write mixed workload improves only 1.11× in throughput, with p99 increasing from 2,720 to 2,834 ms. At one client, mixed throughput is lower on GPU. Optimized SQL remains faster for this mixed workload.

  • Same shared Linkding workload and seed: 100,000 bookmarks, 2,000 tags and 50 users. Simple search uses q=alpha. Complex search uses an eight-term boolean expression; both return 1,000 active matches and a first page of 20. The complex query is synthetic, on the existing seed.
  • Dual AMD EPYC 7502 host, one NVIDIA RTX 3090. Each variant has four server CPUs, four PostgreSQL CPUs and four client CPUs, with disjoint affinity. Four variants run concurrently on a shared host; clocks and NUMA placement are not fixed.
  • Each point starts with a fresh database and server, then 10 s warmup and 30 s measurement. Initial index creation is in warmup; write-triggered invalidation and rebuilding are included in mixed measurements. This measures warm operation, rather than cold start.
  • 72 measurement points, 128,022 measured requests, zero HTTP failures and zero failed response checks. Expanded search conformance also passed 42 requests each on CPU and GPU. Latency figures average per-repetition percentiles; request rate includes k6's graceful stop.
  • These results cover two text searches and the existing mixed scenario at 1 and 16 clients. Earlier overview results use different conditions and remain separate. GPU gains apply to these search workloads; whole-application, cost and power improvements were not established.

Method

Every point reseeds the database, warms up for 10 s and measures for 30 s. The published numbers are means of 3 repetitions.

  • Each server and its PostgreSQL get their own CPUs. In the serial runs, the server has 4 cores and k6 runs on separate cores. Python, Node and Go run 4 workers. Rust runs 4 tokio threads.
  • Requests/s is k6's http_reqs rate over the whole window, including the graceful stop. Latencies are k6 percentiles. RSS is the peak resident memory of the server's whole process tree.
  • Login hashes with bcrypt at cost 12 in every implementation, so that scenario measures bcrypt more than the framework.
  • These are runs on one host. Raw points, summaries and the scripts are in performance/.
