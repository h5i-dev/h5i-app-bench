# Linkding: selectable read SQL modes

Follow-up: [get, creation and search improvements](hotpaths-2026-10-18.md).

This follows the [scalar-membership experiment](scalar-membership-2026-10-18.md).
The engine now exposes two equivalent read SQL strategies, with the original
`IN` spelling as the default. This experiment compares them through real HTTP
list requests at **fixed offset 100**, separating exact-count and page-read timings.

## Implementation and compatibility

Engine commit [`8bec359`](https://github.com/h5i-dev/h5i/commit/8bec359), on
`optimize-read-subqueries`, adds `ReadSqlMode::{Membership, ScalarWhenUnique}`.
Configure the PostgreSQL pool before serving:

```rust,ignore
let pool = h5i_app_pg::pool(&database_url, 32)?;
pool.set_read_sql_mode(h5i_app_pg::ReadSqlMode::ScalarWhenUnique);
let engine = h5i_app_pg::Engine::<App, AppStore>::new(pool, config);
```

`Membership` retains `IN (SELECT ...)`. `ScalarWhenUnique` uses scalar `=` only
when the entire tenant-scoped primary key is fixed by conjunctions of equality
predicates. Other membership predicates retain `IN`. The setting is shared by
pool clones and covers both rows and exact counts, recursively. There is no
automatic dispatch or per-read override yet. `compile_read` keeps its signature
and defaults to Membership; direct callers can use `compile_read_with_mode`.
There are no changes to public configuration struct fields, schema, locks,
isolation, application decisions, read/count plans or generated Lean.

Neither mode is universally faster. Default benchmark dependency pins remain
unchanged; using the experiment needs the mode-enabled engine. The benchmark
hook described below is confined to the disposable instrumented server.

## Fixed-offset HTTP results

Mean of three repetitions, 5 s warmup and 15 s measurement per point. Completed
HTTP requests/second include draining. Both modes use **the same binary**;
only its pool setting changes. PostgreSQL is reseeded and analyzed for every
point. Runs alternate Membership/Scalar, Scalar/Membership, Membership/Scalar.

| Clients | Membership RPS | Scalar RPS | Scalar / Membership | Membership p99 ms | Scalar p99 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 31.20 | 47.86 | 1.53× | 33.63 | 22.38 |
| 64 | 154.11 | 259.12 | 1.68× | 453.17 | 286.38 |

All **12 points, 22,458 HTTP requests, zero failures**. Each request loads 489
physical rows through five row reads and one exact-count query. The diagnostic
response contains 20 results with an exact total of 95,000 in both modes.

| Clients | Count wait ms: Membership → Scalar | Bookmark page wait ms | Tag read wait ms | Link read wait ms |
| --- | ---: | ---: | ---: | ---: |
| 1 | 29.50 → 18.42 | 1.17 → 1.07 | 2.18 → 2.01 | 2.85 → 2.62 |
| 64 | 195.30 → 108.30 | 4.68 → 4.92 | 6.10 → 6.37 | 6.89 → 7.12 |

Timers measure awaited query futures, including preparation and driver/network
wait; pipelined timers overlap and **must not be added together**. At 64 clients,
connection-pool wait falls from 204 to 121 ms/request. The count remains the
critical load operation; page/tag/link waits do not explain the speedup.
RPS standard deviations are 0.12/1.45 at one client and 0.85/1.23 at 64 clients
(Membership/Scalar).

The earlier rotating-offset workload reported a 64-client list regression.
This fixed-offset experiment does **not** reproduce it, but it does not
invalidate that earlier result or isolate its cause. It changes the offset
schedule, runs at a later time, and adds per-read timing probes. The shared host
still has uncontrolled clocks and NUMA placement. Do not interpret these as a
speedup over the original published list benchmark, a cross-language comparison,
or a general guarantee for other offsets. Get, search, writes, Conduit and GPU
variants are not remeasured in this follow-up.

## Execution-plan diagnostic

A separate seeded database captures the actual six SQL statements and their
parameters from one HTTP request per mode. The bound statements are replayed
with `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. This is a single-request
literal-bound diagnostic, not the prepared statement's plan history or another
throughput comparison.

- Membership count: Aggregate → Hash Join, scanning 95,000 active bookmarks
  and joining the token lookup; 47.89 ms.
- Scalar count: token lookup as InitPlan, then a bookmark sequential scan;
  33.31 ms. It still scans 95,000 active bookmarks and rejects 5,000 archived
  rows. The rewrite removes the join; it does not remove the scan.
- Bookmark page: 0.43/0.51 ms, tags: 1.79/1.72 ms, links: 1.09/1.10 ms
  (Membership/Scalar). Both bookmark page plans use an index scan with a limit.

Only [plan summaries](results/sql-modes-2026-10-18/plan-summary.csv) are published.
Captured SQL, PostgreSQL logs, full plans and all raw benchmark files stay in
`/dev/shm`.

## Correctness and proof boundary

Eight SQL-renderer unit tests pass, including default compatibility, identical
parameters for both modes, and preservation of IN for nonunique lookups.
PostgreSQL tests compare 6,400 reads plus pipelined reads and exact counts with
the reference evaluator, using the **same** 3,200 randomized cases in each mode.
Another 120 edge cases per mode cover empty lookups, compound keys, windows,
OR/AND and tenant separation. The bounded statement-cache test passes.

All nine Linkding Hurl files pass in each mode: 200 HTTP requests per mode,
including authentication, pagination, visibility and mutation/search behavior.
The SQL crate's existing Lean gate passes: 203 theorems in four modules,
using only the existing accepted axioms. Application extraction inputs and
proofs are unchanged; the preceding experiment checked its 493-theorem gate.
The read renderer remains differential-tested, **not formally proved**.

## Reproduce and provenance

Both measured modes use the benchmark's existing engine base
`3fcbcdafdfdd759bfa52c765ce8dd2f73c88a26e` plus the mode-enabled renderer and
pool API. This isolates the experiment from unrelated newer engine changes.
The benchmark application base is `ec1b19d2911c387bc0a9bae11c4c33e53351e242`.
The production implementation is based on `b8cbcfd`; the newly fetched main
`31f387e` only changes README and is not substituted into the measurement.

Use fresh disposable worktrees and the current benchmark tooling. Before
instrumenting the pinned engine, export the updated renderer and apply only
the mode API changes from a local h5i clone containing both commits:

```sh
git -C /path/to/h5i show 8bec359:crates/h5i-app-pgsql/src/read.rs \
  > /dev/shm/h5i-probe/crates/h5i-app-pgsql/src/read.rs
git -C /path/to/h5i diff 444e9b5 8bec359 -- \
  crates/h5i-app-pg/src/lib.rs crates/h5i-app-pg/src/table.rs \
  crates/h5i-app-pg/src/statements.rs crates/h5i-app-pgsql/src/lib.rs \
  > /dev/shm/read-mode-api.patch
git -C /dev/shm/h5i-probe apply /dev/shm/read-mode-api.patch
python3 performance/engine-profile/instrument.py \
  /dev/shm/h5i-probe /dev/shm/bench-probe --read-sql-modes
TMPDIR=/dev/shm CARGO_TARGET_DIR=/dev/shm/sql-mode-target \
  cargo build --release --manifest-path performance/linkding/rust-h5i/Cargo.toml -p linkding-server
```

The generator's mode hook and per-read timers were reproduced against the
measurement sources and compared byte-for-byte. Keep non-h5i lockfile entries
unchanged. Repeat the following with mode/order Membership/Scalar,
Scalar/Membership, Membership/Scalar, using a distinct output directory each time:

```sh
python3 performance/engine-profile/run.py --app linkding \
  --binary /dev/shm/sql-mode-target/release/linkding-server \
  --out /dev/shm/membership-r1 --scenarios list --concurrency '1 64' \
  --repeats 1 --warmup 5 --duration 15 --read-sql-mode membership --list-offset 100
```

Use `--read-sql-mode scalar` for the alternate setting. This flag requires the
instrumented Linkding hook generated by `--read-sql-modes`; it is not a
production-server environment variable. `LIST_OFFSET` is an optional workload
override; without it, the existing rotating-offset workload is unchanged.
Four server CPUs, four PostgreSQL CPUs and four client CPUs are disjoint;
four Tokio workers, 32 connections, PostgreSQL 16, 512 MB shared buffers and
1 GiB container shared memory match the preceding experiment. All data/builds
use `/dev/shm`. Hashes, run times and request counts are in
[runs.csv](results/sql-modes-2026-10-18/runs.csv); only summary CSVs are committed.
