# Linkding retrieval, creation and search

2026-10-18. Follow-up to the [single-get](single-get-2026-10-18.md) and
[SQL-mode](sql-modes-2026-10-18.md) experiments. Baseline benchmark source is
`8dfcbc2776a765b26c14d6c156450bbcddd695d5`. The normal application advances
its Rust and Lean dependency pins together from h5i `3fcbcdaf` to
`8e764ab849f71e771bc8d026491a3c104f8cb6a5`.

## Changes

The optimized get route previously authenticated, fetched the bookmark, then
fetched its tag names in three sequential SQL statements. It now fetches the
bookmark and its tag names in one statement after authentication, for two
statements total. The same kernel checks the bookmark's existence and owner
before the HTTP response returns the retained row and tags. Bookmark and tags
now come from one statement snapshot; authentication remains a separate read.

The normal engine application selects `ScalarWhenUnique` for bookmark
creation and nonpaged listings. Other commands keep the pool default
`Membership`, including the original paged-list workload. The new
`Tx::with_read_sql_mode` handle shares the transaction, snapshot and bounded
statement cache without modifying the pool or concurrent requests. This is
an additive engine API; existing applications retain their default behavior.

For creation, PostgreSQL can use the existing owner/URL indexes when the
unique token lookup supplies a scalar owner value. The original membership
form scanned the full bookmark table in this experiment. A diagnostic plan
after inserting the test URL took about 20.09 ms for that bookmark SELECT,
versus 0.20 ms with the scalar rendering. These are diagnostic queries after
the insert, not the original absent-URL lookup or a substitute for HTTP
measurement. [Plan summaries](results/hotpaths-2026-10-18/create-plan-summary.csv).
The global ID-counter lock and SERIALIZABLE isolation remain in place;
reducing work inside the lock reduces queueing without relaxing correctness.

The search rendering improves database work, but does not push text matching
into SQL. Search still materializes about 287,002 physical rows per request
on this seed and evaluates the existing query language in the kernel.

## Measurement conditions

Each point runs the existing authenticated HTTP workload over 100,000
bookmarks and 2,000 tags: authentication, SQL, kernel decisions, writes where
applicable, tag handling, JSON and networking are included. The database is
reseeded and ANALYZEd, and the server restarted before every point. Each point
has five seconds warmup and a 15-second constant-client measurement window.
Get permits five seconds to drain; create/search permit 120 seconds so slow
requests complete. k6 throughput includes the actual measurement/drain runtime.
Percentile columns are means of per-repetition percentiles, not pooled samples.

Three repetitions rotate before/after/reference across these slots:

| Slot | Server CPUs | PostgreSQL CPUs | Client CPUs |
| --- | --- | --- | --- |
| A | 0–3 | 4–7 | 8–11 |
| B | 12–15 | 16–19 | 20–23 |
| C | 24–27 | 28–31 | 32–35 |

Each variant uses four runtime workers, a 32-connection pool, its own
PostgreSQL 16 container with 512 MiB shared buffers and 1 GiB shared memory,
and one TCP connection per HTTP request. Database, caches, scratch and raw
captures are under `/dev/shm`. The host is shared; slot rotation limits some
placement effects but does not remove host-wide contention. Absolute numbers
from earlier runs under different host load are not directly comparable.

A separate diagnostic series alternates membership/scalar pool modes on the
same instrumented binary, three times each, with create and search at 1/64
clients. It uses CPUs 36–39/40–43/44–47 and the same seed/window/drain. Those
figures explain costs and are not the final application's HTTP comparison.

## Safety and validation

The kernels, Rust read/count plans, extracted Lean and theorem sources are
unchanged. The normal application retains its SERIALIZABLE transactions,
read-only snapshots, locks, counters and write sets. The engine's two SQL
renderings use the same declarative predicates; nonunique membership remains
an IN subquery. The mode override test executes both load and count through
both scoped modes and verifies that the pool and original handle remain in
their original mode. Database reference tests include randomized nested
predicates and uniqueness/window edge cases, plus bounded-cache tests.

- Normal application: release tests pass (five tests); Lean gate passes
  493 theorems in nine modules, including ownership, storage and read-plan
  sufficiency. Rust and Lean dependencies use the same new h5i revision.
- Optimized application: release tests pass (two tests); unchanged Lean gate
  passes 16 theorems in one module.
- Existing extracted SQL compiler: Lean gate passes 203 theorems in four modules.
  All gates permit only `propext`, `Classical.choice` and `Quot.sound`.
- PostgreSQL integration: five pg tests and eight pgsql tests pass, including
  6,400 randomized predicate cases and 240 scoped-mode edge cases, each with
  row and exact-count reference assertions. The bounded prepared cache passes.
- Shared API suite: all nine files / 200 requests pass for optimized before,
  optimized after and normal after (600 conformance requests total).
- Full-seed read-only responses are identical across baseline normal, new
  normal and new optimized: list total 95,000 with 20 results, text-search
  total 1,000 with 20 results, and bookmark 1,000 with its tags.


The optimized handler's handwritten SQL and HTTP shell are outside its Lean
proof boundary. Rechecking its kernel does not prove the new SQL or HTTP
handler. Their API behavior is checked by the shared conformance suite.
The normal engine also continues to trust its database/runtime bridge as
before. In particular, `compile_read_with_mode` is outside Lean extraction;
the 203-theorem compiler gate does not prove equivalence of its two read SQL
renderings. That equivalence remains supported by PostgreSQL reference tests
under the existing trust boundary, as documented in
[h5i TRUST.md](https://github.com/h5i-dev/h5i/blob/8e764ab849f71e771bc8d026491a3c104f8cb6a5/docs/app/TRUST.md).
This change does not claim a new end-to-end formal proof.

## Reproduction and retained data

Build the before application at benchmark `8dfcbc2` and the after application
at this revision using `cargo build --release --locked`. Normal application's
Cargo and Lake pins must agree; the after revision pins h5i `8e764ab8`.
Use separate target directories for before/after binaries. Build the shared
Go implementation without changing its logic.

```sh
python3 performance/linkding/bench/remeasure-get.py \
  --before "$OPT_BEFORE" --after "$OPT_AFTER" --go "$NORMAL_BEFORE" \
  --reference-impl rust-h5i --out /dev/shm/linkding-get-new
python3 performance/linkding/bench/remeasure-get.py \
  --before "$NORMAL_BEFORE" --after "$NORMAL_AFTER" --go "$GO_BINARY" \
  --before-impl rust-h5i --after-impl rust-h5i \
  --scenarios 'create search' --drain 120 \
  --out /dev/shm/linkding-routes-new
```

Run these separately with free default ports, or supply `--pg-port` and
`--http-port`. The flags retain compatibility with the earlier get runner;
`--reference-impl` determines the implementation behind `--go`. Binary SHA256
summaries are in the adjacent result directory. Only summary CSV/Markdown is
committed; raw k6 JSON, database plans and process logs stay local.
